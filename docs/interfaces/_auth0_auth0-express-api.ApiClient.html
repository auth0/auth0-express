    getClientCredentialsToken

    • getClientCredentialsToken(
          options: { audience?: string; scope?: string | null },
      ): Promise<TokenSet>

      Acquires an access token using the OAuth 2.0 client credentials grant.

      Requires the client to be constructed with clientId and at least one of clientSecret or clientAssertionSigningKey; throws MissingClientAuthError otherwise.

      The audience defaults to the audience configured at construction time. Pass an explicit audience to override for a specific downstream API.

      Every call performs a token request. This method holds no cache, so a caller that needs one has to add it.

      scope is forwarded to the token endpoint, which needs @auth0/auth0-auth-js 1.18.0 or later, so this package requires that version as a minimum. Whitespace in scope is normalized to single spaces. A null or undefined scope is omitted from the request. A blank or non-string scope throws InvalidScopeError before any request is made, because Auth0 would treat it as omitted and issue the full grant.

      The requested scope does not narrow the token Auth0 issues. Read the granted scope on the result to see what the token actually carries.

      Parameters

      • options: { audience?: string; scope?: string | null }

        Options for the client credentials grant.

        • Optionalaudience?: string

          Target API audience. Defaults to this.#options.audience.

        • Optionalscope?: string | null

          Space-separated OAuth 2.0 scopes. Omit (or pass null) to send no scope parameter.

      Returns Promise<TokenSet>

      Promise resolving to a TokenSet with accessToken and expiresAt, plus the granted scope and tokenType when they are reported. scope is returned exactly as the server sent it. An absent scope means the scopes were granted as requested (RFC 6749 section 5.1), and an empty string means nothing was granted. The two are kept apart, so test for undefined rather than for falsiness.

      Throws

      When no client credentials are configured.

      Throws

      When scope is blank or not a string.

      Throws

      When Auth0 returns an error response.

    getTokenByExchangeProfile

    • getTokenByExchangeProfile(
          subjectToken: string,
          options: ExchangeProfileOptions,
      ): Promise<TokenExchangeProfileResult>

      Exchanges a token via a Custom Token Exchange Profile for a different API audience while preserving user identity (RFC 8693).

      This method supports Custom Token Exchange for custom token types via a configured Token Exchange Profile.

      For Access Token Exchange with Token Vault (external provider's access tokens), use getAccessTokenForConnection instead.

      Note: This method requires a confidential client (client credentials must be configured). While Custom Token Exchange Early Access technically permits public clients, this implementation currently requires client authentication. Public client support may be added in a future release.

      Parameters

      • subjectToken: string

        The raw token to be exchanged (without "Bearer " prefix)

      • options: ExchangeProfileOptions

        Configuration for the token exchange

      Returns Promise<TokenExchangeProfileResult>

      A promise that resolves with the TokenExchangeProfileResult

      Throws

      When client credentials are not configured or exchange fails

      See

      Custom Token Exchange Documentation

      Example

      // Exchange custom token (organization is optional)
      const result = await apiClient.getTokenByExchangeProfile(
        userToken,
        {
          subjectTokenType: 'urn:example:custom-token',
          audience: 'https://api.backend.com',
          organization: 'org_abc123', // Optional - Organization ID or name
          scope: 'read:data write:data',
        }
      );
      // When organization is provided, the access token will include the organization ID in its payload

    getTokenOnBehalfOf

    • getTokenOnBehalfOf(
          accessToken: string,
          options: OnBehalfOfTokenOptions,
          context?: OnBehalfOfTokenContext,
      ): Promise<OnBehalfOfTokenResult>

      Exchanges an Auth0 access token for another Auth0 access token targeting a downstream API while acting on behalf of the same end user (OBO).

      This is a convenience wrapper around getTokenByExchangeProfile that fixes the RFC 8693 token types for Auth0 access-token-to-access-token exchange.

      Note: This method requires a confidential client (client credentials must be configured). The SDK forwards the incoming access token as the subject_token and applies no DPoP-specific handling during the exchange itself.

      Caching

      Pass context.store to cache the exchanged token. The token is cached under the scopes the exchange actually granted, and those scopes are recorded alongside it, so a later call asking for that narrower set is served from cache. scopeMatching on ApiClientOptions selects exact or covering matching; see ScopeMatching.

      In 'strict' mode a repeat request hits only when its requested scopes equal the scopes the earlier exchange was granted. A response without scope means the grant matched the request, so such a request hits. When the grant was narrowed or widened, the entry sits under the granted set and the same request misses and re-exchanges every time. In 'non_strict' mode a request is also served from any cached token whose granted scopes cover it, which needs an IndexedTokenStore.

      A store failure never fails this call. A read that throws, a malformed entry, an entry close to expiry and a failure to derive the cache key on read are all treated as a cache miss, and a write that throws still returns the freshly exchanged token. A cached entry is shape-validated but not integrity-checked, so a store shared with other software is trusted to return exactly what was written to it.

      A token whose claims cannot be keyed unambiguously is never cached. If iss, client_id, azp, sub, org_id, sid or jti is present with a value that is not a string, the call proceeds as an ordinary uncached exchange. A conforming token never does this.

      This method does not reject a result that came back with fewer scopes than were requested. It caches it under what was granted and returns it, with scope set to exactly what the authorization server sent. Deciding whether a narrowed grant is acceptable belongs to the caller, which has the request context needed to turn it into the right response. Use grantedScopes on the result to make that decision: it is always present, on a fresh exchange and on a cache hit alike. scope is not enough, because an authorization server that omits it means the scopes were granted as requested (RFC 6749 section 5.1), while an empty scope means nothing was granted.

      Verifying the subject token

      Caching needs the subject token's claims to derive a cache key, so the token is verified when, and only when, a store is supplied. Without a store the token is forwarded untouched, exactly as it was before caching existed.

      That internal verification runs as a bearer token with no request context, so it cannot satisfy dpop.mode: 'required', accept a DPoP-bound token, or give a domains resolver a URL or headers. Pass context.verified in those cases: verify once at your ingress, where the scheme, the proof and the headers are available, and hand the result in.

      Supplied claims are only trusted when all of the following hold, and the call is rejected otherwise. Claims this instance never produced are an integration bug and throw InvalidConfigurationError; claims that belong to a different token or have expired throw VerifyAccessTokenError with the same challenges as verifyAccessToken:

      • verified.claims is the very object that verifyAccessToken on this same ApiClient instance returned. The check is on object identity, so the claims cannot be serialized, cloned, spread into a new object or sent across a worker boundary, and claims verified by a different ApiClient instance are refused.
      • verified.accessToken equals accessToken, and is the token those claims were verified from.
      • The claims have not expired: exp must be later than the current time plus a few seconds of leeway.

      The cache key is derived from a copy of the claims taken when verifyAccessToken returned them, not from the object you pass in. Adding to or changing the claims object after verification, for example setting sub to another subject, has no effect on the cache key or on which cached token is read or written.

      When an organizationPolicy is configured, it is also applied to that trusted copy of the claims before the cache is read, with the same checks and errors as verifyAccessToken.

      Parameters

      • accessToken: string

        The Auth0 access token to exchange (without "Bearer " prefix)

      • options: OnBehalfOfTokenOptions

        Configuration for the downstream audience and optional scope

      • Optionalcontext: OnBehalfOfTokenContext

        Optional per-call cache and pre-verified subject token

      Returns Promise<OnBehalfOfTokenResult>

      A promise that resolves with the OnBehalfOfTokenResult, including the scopes the exchange actually granted in grantedScopes

      Throws

      When client credentials are not configured, meaning neither a client secret nor a client assertion signing key. This is checked first, before any verification or cache access, even when a client id is set.

      Throws

      When the exchange fails

      Throws

      When a store is supplied and the subject token does not verify

      Throws

      When a store is supplied, organizationPolicy is 'required' and the subject token carries no organization

      Throws

      When a store is supplied and the subject token's organization is not in the configured organizationId allowlist

      Throws

      When context.verified does not match accessToken, or when its claims have expired

      Throws

      When the claims in context.verified were not returned by verifyAccessToken on this same ApiClient instance (object identity is required, so a clone or deserialized copy is rejected)

      Throws

      When scopeMatching is 'non_strict' without an IndexedTokenStore

      Example

      const result = await apiClient.getTokenOnBehalfOf(incomingAccessToken, {
        audience: 'https://api.backend.com',
        scope: 'read:data write:data',
      });

      Example: Cached, with the token verified at ingress

      const claims = await apiClient.verifyAccessToken({
        accessToken: incomingAccessToken,
        scheme: 'dpop',
        dpopProof: request.headers.get('dpop') ?? undefined,
        httpMethod: request.method,
        httpUrl: request.url,
      });

      const result = await apiClient.getTokenOnBehalfOf(
        incomingAccessToken,
        { audience: 'https://api.backend.com', scope: 'read:data' },
        { store, verified: { accessToken: incomingAccessToken, claims } }
      );

    verifyAccessToken

    • verifyAccessToken(
          options: VerifyAccessTokenOptions,
      ): Promise<VerifiedAccessTokenClaims>

      Verifies the provided access token against the ApiClient's configured audience.

      This method validates the JWT signature using the Auth0 tenant's JWKS and verifies standard claims including issuer, expiration, and issued-at time. The audience claim is verified against the audience configured when constructing the ApiClient.

      DPoP support:

      • dpop.mode controls behavior: allowed (default) accepts Bearer or DPoP; required enforces DPoP; disabled ignores DPoP.
      • When validating a DPoP-bound token, you must provide scheme: 'dpop', the dpopProof header value, and the actual httpMethod/httpUrl used for the request.
      • Bearer tokens omit DPoP params; DPoP params are validated together and proof binding is enforced.

      Parameters

      • options: VerifyAccessTokenOptions

        Options containing the access token and optional required claims.

      Returns Promise<VerifiedAccessTokenClaims>

      Promise resolving to the verified token payload containing all JWT claims.

      See

      README.md and EXAMPLES.md for usage in allowed/required/disabled modes.

      Throws

      When verification fails due to invalid signature, expired token, mismatched audience, or missing required claims.

      Example

      @example Bearer token validation
      const apiClient = new ApiClient({
        domain: 'example.auth0.com',
        audience: 'https://api.example.com', // This audience is used for verification
      });
      const payload = await apiClient.verifyAccessToken({
        accessToken: 'eyJhbGc...',
      });

      @example DPoP-bound token validation (allowed/required mode)
      const apiClient = new ApiClient({
        domain: 'example.auth0.com',
        audience: 'https://api.example.com',
        dpop: { mode: 'required' }, // default is 'allowed'
      });
      const dpopPayload = await apiClient.verifyAccessToken({
        accessToken: 'eyJhbGc...',              // JWT with cnf.jkt claim
        scheme: 'dpop',
        dpopProof: 'eyJhbGciOiJFUzI1NiIsInR5cCI6ImRwb3A...', // value from DPoP header
        httpMethod: 'GET',                      // actual request method
        httpUrl: 'https://api.example.com/resource', // actual request URL
      });
